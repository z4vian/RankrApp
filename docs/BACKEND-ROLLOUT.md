# Backend rollout and remaining all-content migration

Status: repository implementation only. Nothing in this change proves the deployed database schema, policies, bucket configuration, function versions, secrets, or client versions. Existing user text still lives in the existing plaintext application columns; the new encrypted store is opt-in and currently has no application feature writing to it. No existing rows are deleted or rewritten. Do not advertise that all content is encrypted by this application layer.

## Safe staging and production order

1. Inventory live schema/policies/grants, storage paths/buckets, user-owned foreign keys, deployed functions, triggers, and every supported client version. Export a restorable database backup and storage manifest; test restoration. Historical `docs/PHASE-*` SQL is evidence of intent, not live configuration.
2. Deploy the photo-compatible client, which understands both old same-project public URLs and durable `storage://` references, including all render surfaces. Old clients using public URLs will lose photo access after the bucket becomes private; coordinate minimum supported versions.
3. Apply migration 001 once through migration tooling after confirming `lists`, `list_items.photo_urls`, and `user_blocks` exist. It makes the bucket private and restrictive guards prevent old broad policies from reopening it. Public-list attachments remain readable by design; private/unattached objects are owner-only. Verify owner, stranger, anonymous, blocked, and cross-owner write/delete cases through real Storage APIs. Previously public files may already be downloaded or cached; changing the bucket flag cannot recall those copies. Verify old public URL behavior and CDN expiry/invalidation during cutover, and use a separately reviewed object migration if immediate server-side old-link revocation is required. The readiness RPC checks the bucket flag, not a full policy audit.
4. Apply migration 002. Generate independent 32-byte cryptographically random AES keys offline/server-side; store canonical base64 values in function secret `RANKR_CONTENT_KEYS`, e.g. JSON mapping a version ID to key material. Set `RANKR_ACTIVE_CONTENT_KEY` to that ID. Never commit keys, print them in logs, put them in `EXPO_PUBLIC_*`, or store them in database configuration accessible to application roles. Back them up in access-controlled recovery storage separately from database backups.
5. Deploy `secure-content` and authenticate smoke tests as two real staging accounts. Exercise create/get/list/update/delete, expired JWTs, tampered ciphertext, stale revision conflicts, and limits. Table and RPC grants must remain service-only. The client helper is an API building block, not automatic migration.
6. Configure a dedicated push server secret and update authorized callers before deploying the hardened push function. The checked-in `supabase/config.toml` sets `verify_jwt = false` only for push so server-secret requests reach its own authentication check; deletion and vault retain JWT checks. Verify unauthorized requests cause no Expo requests. Expo acceptance is not delivery; receipts and retries remain future work.
7. Verify all user-owned FKs cascade from auth and inventory every bucket. Deletion covers list photos in flat UUID folders and legacy root avatars matching exactly `avatar-<caller UUID>-<digits>.jpg`; all other layouts need explicit support. Deploy deletion server before client. Test a storage failure, auth failure, retry, and concurrent upload in staging. The workflow is not atomic: removed files stay removed on later failure. New upload/deletion concurrency and legacy nested/other-bucket content require a deletion lock/job before broad rollout. Current handler fails on nested layout and caps each attempt at 10,000 objects; retries continue cleanup.
8. Observe failure counts and latency without logging payloads, tokens or keys. Keep feature rollout gated until native/web and production-like integration tests pass. Roll back clients/functions if needed; do not reopen a private bucket to conceal a client regression.

## Encryption threat model and key lifecycle

AES-256-GCM uses a random 96-bit nonce and authenticates owner ID, record ID, content type and format version as additional authenticated data. Metadata (ownership, type, IDs, revision, timestamps, ciphertext size) remains visible to database administrators. Keys and service credentials live on the server. The server can decrypt: this is not end-to-end encryption, and it does not defend against a compromised authorized server or keys. TLS is still required. List-item photos become private/access-controlled with platform encryption at rest; existing avatar uploads still use a public bucket and require a separate compatible migration; this patch does not add application encryption to image bytes. Signed URLs are bearer credentials valid for up to 120 seconds; visibility/block changes cannot revoke an already issued URL immediately, and device/browser caches may retain images.

Rotation: add the new key while retaining old keys; switch active ID; read and re-encrypt each record with revision compare-and-swap, retry conflicts from a fresh read. Validate every record and backup retention dependency before retiring old keys. Losing an old key makes its records and backups unrecoverable. Restoring ciphertext without its matching key is not recovery. Revision CAS detects stale writes, but an attacker controlling the DB can replay an entire older valid envelope; there is no external rollback ledger.

## Required route to ALL user content

1. Inventory fields across profiles, lists, list items (titles, notes, photo references), posts, comments, reports, feedback, preferences, local drafts, push payloads, and uploaded bytes. Decide which relational/authorization metadata must remain queryable. Auth credentials are managed by Supabase Auth and are not moved into a generic payload table.
2. Design server APIs preserving public/follower/private visibility, block rules, moderation, feeds, search, counts, ranking, exports and account deletion. The current vault API deliberately exposes owner-only records; simply redirecting existing public content into it breaks social features. Public access needs explicit authorization before decryption, never service-role reads based on client-supplied owner IDs.
3. Replace every direct plaintext write/read with versioned server APIs, enforce minimum supported clients, and prevent old writers. If true all-content application encryption includes files, implement authenticated streaming file encryption and authorized server decrypt delivery; private bucket storage alone is insufficient.
4. Backfill in bounded resumable batches with deterministic source IDs, source-version checks, checkpointing, retry-safe encryption, and reconciliation counts/checksums. Shadow-read and verify behavior, not just record counts. Keep plaintext until reconciliation and restore tests succeed. Include comments, reports, feedback, files and encrypted records in export.
5. Cut reads to encrypted APIs, revoke legacy plaintext access/writes, then remove plaintext columns only after the agreed backup/retention window and an explicit irreversible migration review. Existing backups/logs and client caches also contain old plaintext; document their lifecycle.

No complete migration, data purge, production keys, or production deployment is included here.
